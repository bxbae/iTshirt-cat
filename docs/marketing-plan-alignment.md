# 재헌의 마케팅·판매 사이트 기획안과 고객지원 문서 대조 (v3 반영)

대상: 「마케팅 부서(AI) + 판매 사이트 기획안 v3」(재헌, 개정 2026-10-21, 상태: 제안)
비교한 우리 문서: [고객지원 에이전트 구성안](support-agent-plan.md), [마케팅 ↔ 고객지원 루프](marketing-support-loop.md)

흐름: v1(재헌) → 우리 문서 수정과 요청 5개 전달 → **v3(재헌이 요청 5개를 모두 수용, 결정 대기 6개에 답)** → 이 문서와 우리 문서를 v3에 맞춰 갱신.
이 문서는 **두 문서가 지금 어디서 일치하고 어디가 남았는지**의 기록이다.

표기: 일치 / 수용(재헌이 우리 요청을 받아들임) / 조정(우리가 맞춤) / 결정 대기(팀 합의 필요).

## 4. 아직 다른 곳 · 우리가 답해야 하는 것

### 4-1. `promises`의 `type`과 `condition` (v3가 병환 확인을 요청)

우리 판정이 코드 규칙이므로 **`condition`은 자유 문장이 아니라 코드 값**이 필요하다.

| 제안 | 값 |
|---|---|
| `type` 목록 | `points`(적립금), `coupon`(쿠폰) |
| `condition_code` | 예) `LATE_3D`(예정일보다 3일 이상 지연), `LATE_7D`, `DEFECT_RETURN_OK`(불량 반품 검수 통과), `PURCHASE_IN_PERIOD`(기간 내 구매). 목록은 고객지원 정책표와 일치시킴 |
| `condition` | 사람이 읽는 설명(문장). 계산에는 쓰지 않음 |

고객지원은 `condition_code`가 목록에 없는 약속을 응대·보상에 쓰지 않는다.

### 4-2. 멱등성 키 재요청의 기대 결과

| | 고객지원 문서 | 마케팅(v3) | 조정 |
|---|---|---|---|
| 같은 키로 두 번째 요청 | "중복 요청 거부" | "이전 결과 반환(completed)" | **"새 지급 없음"**을 기준으로 맞춘다. 고객지원 단독 테스트 7번을 "두 번째 요청에도 새 지급이 생기지 않고 이전 결과가 돌아온다"로 수정 |

### 4-3. 문의 접수 이벤트의 발행 주체 (v3 10-2가 병환과 확인하자고 함)

문의 위젯은 병환 소관이므로 **문의 접수 이벤트는 고객지원(위젯)이 발행**한다. 이름은 `support.inquiry_received`(제안), 필드는 `inquiry_id`, `buyer_id`, `order_id`(선택), `channel_code`. 문의 원문은 `untrusted`. 이 이벤트는 마케팅이 구독하지 않으며 통합 에이전트가 사건 판단에 쓴다. 대표 사건 흐름 그림의 1단계를 이에 맞춰 고쳤다.

### 4-4. 요청 요약표의 표기 불일치 (우리 쪽 실수)

이전 대조 문서의 요약표는 요청 4번을 "보상 결과 이벤트", 상세 표는 "현금 환불 API"로 적어 서로 달랐다. v3는 상세 표(**환불 API**)를 따랐고, 보상 결과는 `issue_coupon` Task 결과 회신과 `coupon.issued`로 전달되므로 별도 이벤트는 필요 없다. **우리도 환불 API가 맞는 요청이었다**고 확정한다.

### 4-5. 보상 쿠폰의 사용·소멸 규칙

v3 안건 1은 `purpose_code`로 목적을 나누고 사용·소멸 규칙을 따로 기록하는 조건부 수용이다. 고객지원 의견: 보상 쿠폰은 **고객이 불편을 겪은 대가**이므로 소멸 기한이 이벤트 쿠폰과 달라야 하고, 환불과 합산 사용 여부는 정책 문서에 명시한다. 최종 값은 재헌·병환·태윤 3인 합의.

## 5. v3의 결정 대기 6개와 우리 의견

| # | 안건 | v3 상태 | 고객지원 의견 |
|---|---|---|---|
| 1 | 적립금·쿠폰 | 조건부 수용(3인 합의) | `purpose_code` 분리에 동의 (4-5) |
| 2 | 현금 환불 실행 주체·등급 | 조건부 수용(태윤 확인) | 동의. 고객지원 관문 경유, B(기준 이상 C). 100,000원은 프로토타입 상수로 후보일 뿐이고 재무 기준표가 정함 |
| 3 | 보상 요청 처리 순서 | **수용(제안)** | 동의. 직렬 처리 + `sequence`. 큐가 한 건씩 보내므로 구현 부담 적음. 단 마케팅이 느리면 줄이 밀리므로 **요청별 마감 시각**을 둔다 |
| 4 | C 보류 해제 주체 | **공통안으로 닫힘** (결정 2·6) | safety 보류 큐 하나, 사람 토큰으로 승인·거절, 데모 10분 무응답 시 자동 거절 |
| 5 | 교차검증 거절·타임아웃의 Task 상태 | 조건부 수용(준하·병환 확정) | 동의. 우리 매핑과 같은 원칙 |
| 6 | contextId 단위 | 조건부 수용(준하 확인) | 동의. 문의에서 파생된 보상은 문의 사건의 contextId 승계 |

## 6. 현재 합의된 연동 요약 (v3 기준)

| 번호 | 방향 | 이름 | 형태 | 등급 |
|---|---|---|---|---|
| ① | 마케팅 → 고객지원 | `notice.published`, `campaign.created`(+`promises[]`), `coupon.issued`(+`purpose_code`) | 이벤트(사실) | — |
| ② | 마케팅 → 고객지원 | `notice_check`(선택) | A2A 읽기, 같은 Task 결과 | 읽기 |
| ③ | 고객지원 → 통합(→ 마케팅) | `support.inquiry_surge` | 이벤트 + Task 근거 | — |
| ④ | 고객지원 → 마케팅 | `get_notice`(notice_id 또는 campaign_id) | A2A 읽기 | 읽기 |
| ⑤ | 고객지원 → 마케팅 | `issue_coupon`(compensation, `sequence`, 직렬) | A2A 요청 | 마케팅이 B/C |
| ⑥ | 고객지원 → 판매 사이트 | `shop_refund_payment` (`POST /api/payments/{id}/refund`) | 고객지원 관문 경유 쓰기 | B (기준 이상 C) |

⑥은 마케팅을 거치지 않는 연동이라 루프 그림에는 없고, 구성안의 통신 지도에 있다.

[루프 문서](marketing-support-loop.md)와 [구성안](support-agent-plan.md)은 이 표에 맞춰 갱신했다.

## 7. 「에이전트 공통 구성안」(2026-10-21)으로 닫힌 것

이 문서의 "아직 다른 곳"·"결정 대기" 중 공통안이 정리한 것이다. 공통안이 우리 문서보다 우선한다.

| 안건 | 공통안의 답 |
|---|---|
| C 보류 해제 주체 | safety 보류 큐 하나, 담당자가 대시보드에서 승인·거절, 10분 자동 거절 (결정 2·6, 7장) |
| 교차검증 호출 | `execute()`만 호출, 안전 레이어가 finance `verify_amount`로 라우팅 (후속 13). 마케팅 v3의 "마케팅 → 재무 직접 요청"은 이렇게 읽음 |
| 이벤트 전달 | Redis Streams `events.publish` 하나 (후속 14). `POST /events` 안은 쓰지 않음 |
| 보상 지급 | 판정 support, 지급 marketing `issue_coupon` (후속 9). 현금 환불은 support `refund_request`(B) |
| 문의 이벤트 | `support.inquiry_received`(support, 1차), `support.inquiry_surge`(분류·정책, 2차), 총량 이상은 data (후속 11) |
| 공지 정보 | `notice.published`는 ID만, 본문·`promises[]`는 `get_notice`로만 (후속 10) |
| 교차검증 결과 상태 | 재무 거절 = `completed` + `outcome: rejected_by_review`, 마감 초과 = `canceled`, 실행 오류 = `failed` (후속 12) |
| 이벤트 단계 | 배송·반품·환불 4종은 2차, 스키마는 1차에 함께 정의 (후속 16) |
| 루프 검사 | 새 요청에만 적용, 동기 질의 응답은 같은 Task의 결과 (5장) |

아직 열린 것: 적립금·쿠폰 소멸 규칙, 요청별 마감 시각 값, 현금 환불 기준 키, `return.received` 필드 — [부족한 점 보고서](support-gap-report.md).
