# 마케팅 ↔ 고객지원 대외 소통 루프

「기획개발 ↔ 인사운영 개선 루프」와 같은 구조로 마케팅 에이전트(`marketing`, 재헌)와 고객지원 에이전트(`support`, 병환)의 연동을 정리한 문서다.
조직도에서 두 부서를 잇는 점선 "대외 소통"을 구체화한 것이고, 공지·상품 관리(마케팅)와 문의 응대·보상 계산(고객지원)이 서로의 기록을 주고받는 고리다.

상위 문서: [고객지원 에이전트 구성안](support-agent-plan.md) · 팀 공통 규약(2026-10-21).
표기: **[제안]** 합의 전, **[규약]** 팀 공통 규약 그대로, **[현재 코드]** 이 저장소 프로토타입에서 이미 되는 것.

---

## 1. 한눈에 보기

```
 마케팅 Agent                                         고객지원 Agent
 공지 · 상품 관리                                      문의 응대 · 보상 계산
 ─────────────────                                    ─────────────────────
        │  ① 이벤트·로그   (비동기)  ───────────────────▶  │
        │     공지·프로모션·상품 변경을 결정 이유와 검토한 대안과 함께
        │                                                  │
        │  ② 질의: 이 문구, 과거에 분쟁이 된 적 있나요? ──▶  │   (동기)
        │  ◀──────────────  판정·경고 응답: 위험 문구 + 근거 카드 → 공지 초안에 경고로 첨부
        │                                                  │
        │  ◀────────────  ③ 공지·FAQ 초안 제안   (비동기)   │
        │     반복 문의 패턴 자동 분석 · 게시는 마케팅이 결정
        │                                                  │
        │  ◀────────────  ④ 진행 중 공지·이벤트 조회  (읽기 전용)
        │     문의 응대·보상 계산 때 자동
```

| 번호 | 방향 | 방식 | 무엇을 주고받나 | 규약상 종류 |
|---|---|---|---|---|
| ① 이벤트·로그 | 마케팅 → 고객지원 | 비동기 이벤트 | 공지 게시·수정·종료, 프로모션·쿠폰 시작·종료, 상품 품절·재입고·가격 변경. **결정 이유와 검토한 대안**을 함께 | A2A 이벤트 |
| ② 질의 | 마케팅 → 고객지원 | 동기 질의 | "이 공지·프로모션 문구가 정책과 충돌하거나 과거 분쟁을 부른 적 있나요?" ← 판정·경고와 근거 카드 | A2A 요청, 읽기 skill |
| ③ 공지·FAQ 초안 | 고객지원 → 마케팅 | 제안(초안) | 반복 문의 패턴을 분석해 공지·FAQ 초안을 제안. **생성·게시는 마케팅이 결정** | A2A 요청 (제안 큐) |
| ④ 진행 중 공지·이벤트 조회 | 고객지원 → 마케팅 | 조회(읽기 전용) | 지금 유효한 공지·프로모션·쿠폰·품절 정보. 문의 응대와 보상 계산 때 자동 | MCP 또는 A2A 읽기 skill |

### 연동 규칙 (이 루프의 헌법)

1. **판정 문장은 고객지원 한 곳에서만 만든다.** 공지가 정책·약속과 충돌하는지, 과거 분쟁이 있었는지의 판정은 고객지원이 하고, 마케팅은 그 결과를 첨부만 한다.
2. **고객지원은 읽기만 하고, 공지는 초안까지만 제안한다.** 고객지원이 공지를 직접 게시하거나 상품·쿠폰을 바꾸지 않는다.
3. **공지 게시·상품 변경은 마케팅이 결정한다.** 고객지원의 경고·초안은 판단 재료이고, 마케팅이 무시할 수 있다 (단, 무시한 사실은 기록).
4. **모든 연동은 자동으로 오간다.** 사람이 중간에서 전달하지 않는다. 대신 규약의 안전장치(contextId, 실행 관문, 근거 첨부)가 전부 적용된다.

> 인사운영 루프에서 "판정 문장은 인사운영 한 곳", "티켓 생성은 기획개발이 결정"이던 것과 같은 분업이다. 역할 대응은 다음과 같다.
>
> | 기획개발 ↔ 인사운영 | 마케팅 ↔ 고객지원 |
> |---|---|
> | 기획개발: 티켓·배포를 결정, 이벤트·로그를 보냄 | 마케팅: 공지·상품을 결정, 이벤트·로그를 보냄 |
> | 인사운영: 기록을 쌓고 판정·경고, 개선 티켓 초안 제안 | 고객지원: 문의·판정 기록을 쌓고 판정·경고, 공지·FAQ 초안 제안 |
> | 기각된 안과 근거 카드 | 과거 분쟁·문의 사례와 근거 카드 |

## 2. 연동별 상세

### ① 이벤트·로그 (마케팅 → 고객지원)

마케팅이 공지·프로모션·상품 상태를 바꿀 때마다 고객지원에 알린다. 고객지원은 이를 **공지 카드**로 저장하고, 이후 문의 응대의 근거로 쓴다.

**공지 카드** [제안]

```json
{
  "context_id": "ctx-notice-2026-1021-001",
  "tenant_id": "<확인 필요 7>",
  "kind": "notice | promotion | coupon | product_change",
  "status": "published | scheduled | ended | canceled",
  "title": "배송 지연 안내와 보상",
  "public_text": "10/20~10/22 출고 주문은 평소보다 1~2일 늦을 수 있습니다.",
  "valid_from": "2026-10-21T00:00:00Z",
  "valid_to": "2026-10-25T00:00:00Z",
  "affects": { "product_ids": [], "categories": ["book"] },
  "promises": [ { "type": "points", "amount": 1000, "condition": "예정일보다 3일 이상 지연" } ],
  "decision_reason": "물류 지연이 3일 이어져 고객 문의가 늘고 있음",
  "alternatives_considered": ["공지 없이 문의별 안내", "전체 쿠폰 지급"],
  "evidence": { "queries": [], "refs": [] },
  "untrusted": { }
}
```

- `promises`가 핵심이다. 마케팅이 고객에게 한 약속을 **구조화된 값**으로 받아야 고객지원이 보상 계산에 정확히 쓸 수 있다. 문장에서 금액을 뽑아내지 않는다 (규약 "숫자는 코드가 산출").
- 고객지원은 `status = published`이고 기간 안인 카드만 응대 근거로 인용한다. 예정·종료·취소 카드는 인용하지 않는다.
- 공지 본문은 외부로 나가는 문구이지만 판매자·고객 입력을 포함할 수 있으므로 **지시로 해석하지 않는 데이터 필드**로만 다룬다 (규약 신뢰 경계).
- [현재 코드] 정책 문서는 `app/kb/*.md` 정적 파일이다. 공지 카드는 **기간이 있는 임시 근거**라서 별도 저장소(공지 카드 테이블)와 검색 대상 추가가 필요하다.

### ② 질의: 이 문구, 과거에 분쟁이 된 적 있나요? (마케팅 → 고객지원, 동기)

마케팅이 공지·프로모션 **초안을 게시하기 전에** 묻는다. 고객지원은 코드 규칙과 과거 사례로 판정해 경고를 돌려준다.

**요청**: `notice_check` skill, 입력 `{ context_id, draft: { title, public_text, promises[], valid_from, valid_to }, untrusted }`.

**응답** (판정은 항상 이 구조):

```json
{
  "verdict": "ok | warn | block",
  "findings": [
    {
      "code": "ABSOLUTE_WORDING",
      "level": "block",
      "message": "'무조건 전액 환불'은 전자책·주문제작 굿즈의 단순변심 환불 불가 규정과 충돌합니다.",
      "evidence": { "policy_refs": ["KB-REF-01#3"], "cases": ["inq-1042", "claim-88"] }
    }
  ],
  "similar_cases": [ { "id": "inq-1042", "summary": "전액 환불 문구를 보고 전자책 환불을 요구", "outcome": "자동 거절 후 불만" } ],
  "computed": { "max_exposure_points": 12000, "basis": "예상 대상 주문 × 약속 금액 (코드 계산)" }
}
```

- 판정은 규칙(코드)이 하고, LLM은 설명 문장을 다듬는 데만 쓴다. 노출 금액처럼 숫자는 코드가 계산한다 (규약).
- 마케팅은 이 응답을 **공지 초안에 경고로 첨부**한다. 첨부된 경고를 보고 문구를 고칠지, 그대로 게시할지는 마케팅이 정한다. 단 `block`을 무시하고 게시하면 감사 로그에 남기고 대시보드에 표시한다 [제안].
- [현재 코드] 이미 있는 재사용 자산:
  - 답변 가드(`copilot/validate.py`)의 단정적 표현(`무조건`, `100%`, `즉시 환불`), 정책에 없는 금액 약속, 조건부 정책(전자책·주문제작) 검출.
  - 정책 수치(`rules/policy.py`)와 규칙→정책 문서 매핑.
- 새로 필요한 것: ① 가드를 "고객 답변"뿐 아니라 "공지 초안"에도 쓰도록 일반화, ② 과거 문의·클레임에서 유사 사례를 찾는 **사례 카드 저장소**(현재 문의는 있지만 검색 가능한 사례 색인이 없음), ③ 약속 금액 × 예상 대상 수 노출 계산.

### ③ 공지·FAQ 초안 제안 (고객지원 → 마케팅)

고객지원이 문의 패턴을 자동으로 분석해, 마케팅에 공지나 FAQ **초안을 제안**한다. 만들지 말지는 마케팅이 정한다.

**감지 규칙(코드)** [제안]

| 패턴 | 조건 예 | 제안 |
|---|---|---|
| 카테고리 급증 | 같은 분류 문의가 최근 24시간에 평소 대비 N배 | 해당 이슈 공지 초안 |
| 반복 질문 | 같은 정책 조항(`KB-DEL-01#2` 등)을 인용한 문의가 N건 이상 | FAQ 초안 |
| 약속 오해 | 같은 공지 카드에서 파생된 자동 거절이 N건 이상 | 문구 수정 제안 (②와 연결) |
| 상품 문제 | 같은 상품의 불량 신청이 N건 이상 | 상품 점검·판매 중지 검토 제안 (마케팅·상품MD와 기획개발 티켓) |

**제안 초안**

```json
{
  "context_id": "ctx-support-pattern-2026-1021-003",
  "pattern": "delivery_delay_spike",
  "evidence": { "queries": ["문의 분류별 24시간 집계"], "case_ids": ["inq-1101", "inq-1102"], "counts": { "now": 37, "baseline": 6 } },
  "draft": { "title": "배송 지연 안내", "public_text": "…", "promises": [] },
  "reason": "배송 문의가 평소의 6배로 늘었고 같은 안내를 반복해서 보내고 있음",
  "caveats": ["보상 약속은 포함하지 않았음. 포함하려면 재무/정산 기준표 확인 필요"]
}
```

- **초안까지만**: 고객지원은 `promises`를 비워 두거나 정책표에 이미 있는 값만 넣는다. 새로운 보상 약속은 제안하지 않는다 (금액 기준은 재무/정산 소관).
- 제안은 마케팅의 **제안 큐**에 들어가고, 마케팅이 채택·보류·기각을 기록한다. 기각 사유는 다음 ② 질의의 재료가 된다 (인사운영 루프의 "기각된 안" 카드와 같은 역할).
- [현재 코드] 대시보드의 분류별 집계(`by_category`)와 가드 적발 통계가 있다. 시간대별 기준선 비교와 제안 생성은 새로 만든다.

### ④ 진행 중 공지·이벤트 조회 (고객지원 → 마케팅, 읽기 전용)

문의를 응대하거나 보상액을 계산하기 전에 자동으로 마케팅의 현재 상태를 읽는다.

| 조회 | 쓰임 |
|---|---|
| 유효한 공지·프로모션 목록 (기간·약속 값) | 고객이 "공지에서 봤다"고 할 때 근거 확인, 답변 초안에 인용 |
| 진행 중 쿠폰·이벤트 | **보상 적립금과 이벤트 쿠폰의 중복 지급 방지**, 쿠폰 사용 조건 문의 응대 |
| 품절·재입고 상태 | 재입고 문의 응대 (일정을 약속하지 않고 공지된 사실만 안내) |
| 상품 정보(가격·할인율 변경) | 영수증 가격과 현재 가격이 다를 때 설명 |

- 읽기 전용이므로 등급 대상이 아니다. 근거(조회 시각, 대상 ID)를 결과에 첨부한다 [규약].
- 조회는 **공통 봉투** `{ok, collected_at, data, truncated}`와 목 모드를 따른다 [규약, common-mcp]. 도구 이름 예: `marketing_get_notices`, `marketing_list_promotions` [제안].
- 보상 지급 직전에 자동 조회하여 중복·충돌이 있으면 `compensation_pay`를 B 등급 교차검증 단계에서 경고로 올린다.
- 마케팅 DB를 고객지원이 직접 읽지 않는다. 마케팅이 제공하는 API·읽기 전용 뷰로만 읽는다 (규약 "데이터 공유", 모노레포 계약).

## 3. 고객지원 자동화 흐름 (자동 / 사람 / 입력 / 카드)

인사운영 Agent 자동화 흐름과 같은 읽는 법이다. 사람은 **확인·승인과 짧은 답변**만 하고 나머지는 자동이다.

| 순서 | 단계 | 구분 | 내용 | 산출물 |
|---|---|---|---|---|
| 1 | 문의 접수·신청 | 입력 | 판매 사이트 문의 위젯, 클레임 신청 | 문의 |
| 2 | 자동 분류·정책 검색 | 자동 | 개인정보 마스킹, 분류, 근거 검색 (**[현재 코드]**) | 분석 카드 |
| 3 | 영수증·정책 판정 | 자동 | 규칙 엔진 (**[현재 코드]**) | **판정 카드**: 결과·금액·규칙 번호·근거 |
| 4 | 마케팅 조회 (④) | 자동 | 유효 공지·쿠폰·품절 확인 | 공지 근거 |
| 5 | 답변 초안·가드 | 자동 | 초안 3종, 약속·금액 검증 (**[현재 코드]**) | 초안 |
| 6 | 빈 자리 질문 | 자동 | 사진 요청 등 고객에게 짧게 질문 (**[현재 코드]** `needs_info`) | 질문 |
| 7 | 승인 | **사람** | 한도 초과·영수증 불일치·검수 불일치 등만 확인·승인 (규약상 C 등급 처리 방식은 확인 필요) | 승인 기록 |
| 8 | 자동 발송·지급 | 자동 | 실행 관문 → 등급 판정 → 발송·지급 | 실행 결과 |
| 9 | 사건 카드 기록 | 카드 | 사건 요약·판정·근거를 카드로 저장, 인사 에이전트에 전달 | **사건 카드** |
| 10 | 패턴 분석 (③) | 자동 | 사건 카드가 쌓여 공지·FAQ 초안의 재료가 됨 | 제안 초안 |

사건 카드가 다음 응대의 재료(유사 사례 근거)와 ③의 재료가 되어 고리가 닫힌다.

## 4. 규약 적용

### 4-1. skill과 등급 (고객지원이 새로 갖는 것)

| skill | 방향 | 하는 일 | 등급 | 요청 가능 에이전트(ACL, 제안) |
|---|---|---|---|---|
| `notice_check` | 수신 (②) | 공지·프로모션 초안 판정 | 읽기 (등급 없음) | marketing, 통합 |
| `notice_card_register` | 수신 (①) | 공지 카드 저장 | A | marketing |
| `notice_draft_propose` | 발신 (③) | 마케팅 제안 큐에 초안 등록 요청 | A | — (마케팅의 skill을 호출) |
| `marketing_get_notices` 등 | 발신 (④) | 유효 공지·프로모션 조회 | 읽기 | — (MCP 또는 마케팅 읽기 skill) |

- 마케팅의 `notice_publish`(공지 게시)는 규약 예시대로 **A 등급**이고 마케팅이 신고한다. 쿠폰 지급·대규모 이벤트는 B 이상이 될 수 있으니 재헌이 신고한다.
- 고객지원은 ③에서 제안만 하므로 실행 관문 대상 액션이 없다. ③이 `promises`로 금액을 담는 경우에도 지급이 아니라 제안이다.

### 4-2. Task 확장 필드 사용

| 필드 | 이 루프에서의 쓰임 |
|---|---|
| contextId | 공지 하나·패턴 하나가 하나의 사건. ①~④ 모두 같은 contextId |
| 마감 시각 | ②는 동기 질의이므로 짧게(예: 수 초~수십 초). 초과 시 마케팅은 경고 없이 게시하지 않고 보류 보고 |
| 경로 | `marketing → support → marketing`처럼 되돌아오는 경로는 루프 거부 대상일 수 있음. ②의 응답은 새 Task가 아니라 같은 Task의 결과로 돌려준다 [제안] |
| 근거 | ②의 `findings.evidence`, ③의 `evidence`가 이 필드에 들어간다 |
| untrusted | 공지 본문·고객 문의 원문 등 외부 문구 |

### 4-3. 해서는 안 되는 것 (README "하지 않는 것"에 추가)

- 고객지원은 공지·프로모션·상품·쿠폰을 직접 바꾸지 않는다.
- 마케팅은 고객지원의 내부 판정 근거(반복 신청 점검 점수 등)를 받지 않는다. ②의 응답에도 포함하지 않는다.
- 공지 문구에서 금액을 정규식으로 추출해 지급 계산에 쓰지 않는다. `promises` 구조화 값만 쓴다.
- 후기 삭제·별점 조건의 보상 공지를 승인하지 않는다 (현재 정책은 후기 삭제 조건만 금지하므로, **별점·내용 조건 보상 금지 조항을 정책 문서에 추가**해야 한다) [제안].

## 5. 대표 시나리오

### 시나리오 A: 배송 지연 급증 → 공지 → 문의 감소 (③ → ① → ④)

1. 고객지원이 배송 문의가 평소의 6배임을 감지 (코드 규칙).
2. ③ 공지 초안(`promises` 없음)을 마케팅 제안 큐에 등록, 근거로 문의 사례 ID와 집계 쿼리를 첨부.
3. 마케팅이 채택하고, 필요하면 ②로 문구를 점검한 뒤 공지 게시 (A 등급).
4. ① 이벤트·로그가 고객지원에 도착, 공지 카드로 저장.
5. 이후 배송 문의는 ④로 유효 공지를 읽어 답변 초안에 인용한다.
6. 대시보드에서 공지 전후 문의량 변화를 본다.

### 시나리오 B: 위험한 프로모션 문구를 게시 전에 차단 (② 경고)

1. 마케팅 초안: "지금 사면 무조건 전액 환불".
2. ② `notice_check` → `block`: 단정적 표현, 전자책·주문제작 굿즈 환불 불가 규정과 충돌(`KB-REF-01#3`), 과거 유사 사례 첨부.
3. 마케팅이 경고를 보고 문구를 고쳐 다시 질의 → `ok` → 게시.
4. 만약 무시하고 게시하면 감사 로그와 대시보드에 "block 무시 게시"로 기록된다.

### 시나리오 C: 쿠폰 이벤트와 보상 중복 방지 (④)

1. 마케팅이 "이번 주 구매자 전원 적립금 1,000원" 이벤트 진행 중.
2. 고객이 배송 지연 보상(적립금 1,000원)을 신청.
3. 보상 지급 전 ④가 진행 중 이벤트를 조회, 이미 같은 목적의 적립금이 지급됐는지 확인.
4. 중복이면 `compensation_pay` 교차검증(B)에서 경고로 올려 재무/정산이 판단.

## 6. 저장소와 폴더 배치 (모노레포 + 독립 패키지) [제안]

팀 설계(통합 시연이 핵심이므로 모노레포로 시작하되, 부서 폴더를 독립 패키지처럼 만든다)에 맞춘 고객지원·마케팅 관련 배치다. 이 방식은 아직 결정 기록에 없으므로 합의 후 확정한다.

```
ax-backend/                         Python · uv workspace
├─ contracts/                       원본 · 2명 승인 (schemas · data-access · openapi)
│   └─ schemas/  notice_card.json, notice_check.json, notice_draft.json   ← 이 문서 2장의 스키마
├─ agent-template/                  execute 구현 · 준하
├─ orchestrator/ · safety/ · memory/
├─ shop-api/                        판매 사이트 서버 · 재헌
├─ dashboard-api/                   공통 로그 저장소만 읽음 · 병환
└─ agents/                          CI 통과 시 자동 머지
    ├─ support/                     고객지원 · 병환  ← 독립 패키지
    │   ├─ pyproject.toml · README.md(5항목) · Dockerfile · .env.example
    │   ├─ src/support/  rules/ claims/ queue/ copilot/ kb/ notices/
    │   └─ tests/
    └─ marketing/                   마케팅 · 재헌
ax-frontend/                        React · Vite · npm
├─ dashboard-web/                   대시보드 화면 · 병환 (고객지원 탭, 연동 현황)
└─ types/                           openapi에서 자동 생성 · 수정 금지
```

| 규칙 | 고객지원에서 지킬 것 |
|---|---|
| 독립 패키지: import 금지, DB는 API·뷰로만 | `agents/support`는 `agents/marketing`을 import하지 않는다. 마케팅 데이터는 ④의 API·MCP로만 읽는다 |
| 데이터 접근은 계약으로 | 공지 카드·질의·제안 초안 형식은 `contracts/schemas`에 정의하고 2명 승인을 받는다 |
| 대시보드는 공통 로그 저장소만 읽음 | `dashboard-api`는 support·marketing의 DB를 직접 보지 않는다. 연동 현황(①~④ 건수, 경고 무시 게시)은 공통 로그로 받는다 |
| CODEOWNERS는 공유 폴더만 | `agents/support`는 병환이 소유하고 CI 통과 시 자동 머지. `contracts/`, `agent-template/` 변경은 승인 필요 |
| CI에서 LLM은 mock | 현재 프로토타입의 mock 제공자와 테스트가 그대로 맞는다. 실제 호출은 서버 PC 시나리오 테스트에서만 |
| 프로젝트 후 `git filter-repo`로 폴더를 이력째 독립 레포로 분리 | 포트폴리오용으로 `agents/support`를 단독 레포로 뺄 수 있도록 다른 폴더 의존을 만들지 않는다 |

[현재 코드] 이 저장소의 `backend/app/{rules,claims.py,queue.py,copilot,kb}`가 `agents/support/src/support/`로 이동할 대상이다. `shop.py`, `api_shop.py`, 쇼핑몰 화면은 판매 사이트(재헌)로 가거나 참조 구현으로만 남긴다 ([구성안 15장](support-agent-plan.md)).

## 7. 개발 순서 (이 루프 기준)

| 단계 | 할 일 | 의존 |
|---|---|---|

| 4 | 목 마케팅 클라이언트(④)와 목 이벤트(①)로 단독 테스트 | common-mcp 규격 |

| 7 | 대시보드에 연동 현황 화면 (공지 전후 문의량, 경고 무시 게시, 제안 채택률) | dashboard-api |

단계 2·3은 다른 사람의 규격을 기다리지 않고 지금 시작할 수 있다.

## 8. 확인 필요

| # | 질문 | 제안 |
|---|---|---|
| 1 | ② 질의의 `block`을 마케팅이 무시하고 게시할 수 있는가 | 무시는 허용하되 감사 로그·대시보드에 기록 (판단은 마케팅). 금전 약속이 포함되면 재무/정산 교차검증 필요 여부는 재무/정산과 협의 |
| 2 | ②의 응답이 `marketing → support → marketing` 경로를 만들어 규약의 루프 거부에 걸리는가 | 같은 Task의 결과로 반환 (새 요청 아님). 템플릿(준하) 확인 필요 |
| 3 | 공지 카드의 `promises`를 마케팅이 구조화해서 보내줄 수 있는가 | 필수 필드로 요청. 없으면 고객지원은 해당 약속을 응대에 쓰지 않음 |
| 4 | contextId 단위 | 공지 1개 = 사건 1개. 문의에서 파생된 경우 문의의 contextId를 이어받는지 통합 에이전트와 확인 |
| 5 | ③ 패턴 감지 임계값(N배, N건) | 초기값은 고객지원이 제안하고 데이터분석과 조율 |
| 6 | 마케팅·상품MD의 상품 관리 중 어디까지가 ④의 조회 범위인가 | 가격·할인·품절·재입고 상태까지 |
| 7 | 별점·내용 조건 보상 금지 정책 추가 | 정책 문서에 조항 추가 (고객지원 소관) |
| 8 | 모노레포 + 독립 패키지 배치 확정 | 결정 기록에 한 줄 추가 후 이 문서 6장을 확정으로 변경 |
| 9 | 고객지원 승인 단계(사람)와 C 등급 보류의 관계 | [구성안 14장 확인 필요 1](support-agent-plan.md)과 같은 안건 |
